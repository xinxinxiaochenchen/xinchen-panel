# 多跳线路与权重切换设计

状态：设计草案，待用户确认 Agent 间 mTLS 中继方案后实施。

## 范围与现状

控制面已有 `lines`、有序 `line_hops`、`priority`、`weight`、套餐 `max_hops` 与 Agent 完整快照。当前创建接口、代理连接、订阅导出和编译器只执行单跳；Agent 证书仅有 ClientAuth 用途。此设计先交付 TCP 多跳与权重选择，再单独交付 UDP 多跳。原有单跳行为和公网纯 IP 只读入口保持兼容。

线路示例：用户 → 香港入口 → 日本中继 → 美国出口。入口终止客户端 Trojan TLS，出口只向管理员目标策略允许的公网地址建立连接；中继不接受任意目标或下一跳。用户流量只在入口按连接、线路和账期快照计量一次。

## 方案选择

1. **Agent 间直接 mTLS 中继（采用）**：数据流只经过线路节点，控制面只下发配置和观测状态。每跳需要可验证的服务端身份和入站端口；认证与配置更复杂，但控制面不承担用户流量。
2. 控制面转送数据：跨 NAT 简单，但控制面会承担所有用户带宽并成为数据面单点故障；不采用。
3. 外部 WireGuard overlay：可复用隧道，但需要额外网络编排、私钥生命周期和内核权限；不纳入这一阶段。

## 数据模型与线路校验

- `line_hops` 位置从 0 连续递增，2–8 跳不得重复节点。首跳角色为 `ingress`，中间为 `relay`，末跳为 `egress`；单跳继续用 `egress`。入口节点需具备 `proxy` 能力及代理端口，中继和出口节点需具备 `forward` 能力。若末跳也承载直接代理，可同时具备 `proxy`。
- 创建、修改、启用线路时，在同一事务中锁定涉及的节点、资源组和订购授权；检查启用状态、能力、所有 hop 的资源组授权和 `max_hops`。共享线路需要显式线路授权；自有线路需要自建许可和数量限制。
- 新增只由控制面配置的每节点中继监听地址与端口。节点不得把中继端口与代理或用户转发端口共用；由数据库端口预留约束防止竞态。
- 已有单跳线路无需数据迁移；新增配置字段采用可选字段和新 migration。控制面与 Agent 的能力版本不满足要求时，拒绝编译多跳线路并保持它不可导出。

## 节点间身份与线路授权

- 节点间 TLS 1.3 双向认证。Agent 使用现有 Ed25519 客户端证书证明来源节点；接收中继的 Agent 使用由专用 Agent CA 签发的 ServerAuth 证书，SAN 绑定控制面登记的中继域名或公网 IP。ServerAuth 证书通过独立 CSR 签发和续期，不把 CA 私钥下发到节点。
- 出站 Agent 验证 CA、SAN 与预期下一跳节点 ID；入站 Agent 验证客户端证书的 CA、URI 节点 ID、有效期和本地快照中的允许来源。只信任 TLS 证书而不检查线路授权不够，因为同一节点可能运行多条不同租户线路。
- 每条线路每个有向 hop 在完整快照中都有控制面生成的随机 256 位 `route_secret`，仅分发给相邻两端。TLS 握手后的 `OPEN` 帧包含线路 ID、连接 ID、目的地址和该边的证明；接收端以常量时间比较当前快照中该线路/来源节点的证明，再从自己的快照读取下一跳。证明不写日志或数据库审计 JSON，配置存储只保留加密或摘要形式。配置撤销、节点停用、订购到期时撤销新连接并按现有 drain 策略关闭存量连接。
- 入站中继每条线路、每来源节点限制并发数和握手速率；`OPEN` 帧固定最大长度，限制 host、port、hop count 和超时。中继不得接受客户端指定的任意下一跳、私网目标或绕过目标策略的地址。

## 控制面配置与数据流

- 编译器从一个 PostgreSQL 一致性快照读取线路、hop、节点健康、Agent 能力、有效订购快照及代理连接。每个 Agent 得到自己的完整中继配置；相邻两端的线路版本和 `route_secret` 必须一致。多节点版本发布无法跨 Agent 原子提交，因此入口只有在所有下游 Agent 已 ACK 同一线路世代且在线时才启用新入口凭据或导出订阅。
- `proxy_config` 记录入口线路 ID、下一跳节点与线路世代。`relay_config` 记录本节点允许的上一跳、下一跳或出口角色、连接数上限和有效期。整个配置参与同一 SHA-256 摘要，Agent 原子预绑定并应用；未知字段和旧 Agent 能力不得静默忽略。
- 入口接收 Trojan 请求后先完成用户额度准入，再建立到下一跳的 mTLS 中继连接；逐跳将 `OPEN` 转发到末跳。末跳执行现有公网地址解析与目标策略检查后拨号。成功回执后双向转发字节；错误以有限错误码返回，任何跳失败都关闭整条链。
- 流量计量只在入口，包括用户上传和下载有效载荷。中继与出口上报 CPU、网卡和连接数等运维指标，但不向用户账本重复记账。入口连接固定线路、倍率和账期；线路切换只影响新连接。

## 权重与故障切换

- 一个用户的多个可用线路可组成选择池。先取最小 `priority` 的健康线路层，再按正整数 `weight` 进行加权选择。使用稳定连接 ID 的哈希作为抽样输入，使一次连接固定线路且重试不会在无状态中随机漂移。
- 健康条件包括所有 hop 节点启用、Agent 45 秒内在线、同一线路世代已 ACK、证书和租约未过期。健康是控制面发布和订阅可用性的门槛；实际连接前仍由 Agent 复核本地配置有效期。
- 新连接在选中线路不可达时可按相同优先级的确定顺序尝试其他健康线路，再尝试下一优先级。每次重试都不重复预留用户额度；只在入口建立一条逻辑计量连接。活跃连接不自动迁移。
- 订阅格式若无法表达服务端自动加权，导出已应用的线路节点与清楚的优先顺序，不伪称客户端支持权重。控制台显示实际可用线路、权重和最近一次选择原因。

## 故障、安全与兼容

- 缺失任何下游 ACK、证书、线路证明或 Agent 能力时不开放多跳入口，也不导出对应代理连接。一个坏线路不能阻止其他线路撤销或发布。
- 端口绑定失败导致该 Agent NACK 并保留旧配置；控制面不把它计为该线路已就绪。Agent 断线、证书吊销、节点停用和订购失效时撤销入口和中继配置。控制流断线关闭数据运行时，行为与当前单跳一致。
- 旧版本 Agent 不接收包含 `relay_config` 的快照；控制面按能力门槛过滤或 NACK。单跳快照摘要和订阅输出保持现有格式。
- 控制面日志只记录线路 ID、节点 ID、世代、错误码与请求 ID；不记录路由证明、用户 Trojan 密码或订阅 Token。

## 验收

1. 三个隔离 Agent 组成入口 → 中继 → 出口，真实 TCP 客户端访问公网测试目标，回包正确；入口账本只有一条逻辑连接的上传/下载量。
2. 未授权来源证书、错误 `route_secret`、重放的旧线路世代、目标私网地址和重复/环路线均被拒绝。
3. 停用中继节点或删除订购后，入口不再导出该线路且新连接拒绝；单跳线路继续工作。
4. 权重选择在固定样本上符合预期比例，优先级与健康门槛生效；同一连接 ID 重试选择稳定。
5. TCP 多跳通过后再设计 UDP 帧格式、会话键、空闲回收和数据报大小边界，避免把 TCP 字节流语义套用于 UDP。
